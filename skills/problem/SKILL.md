# 問題発見・課題定義フレームワーク

ユーザーの $ARGUMENTS に基づき、以下のフレームワークから適切なものを適用してください。引数がなければ状況をヒアリングして提案してください。

---

## 01. As is／To be
**目的**: 現状（As is）と理想（To be）のギャップを明確にし、取り組むべき課題を定義する

**テンプレート**:
| 項目 | As is（現状） | To be（理想） | Gap（差分） |
|------|-------------|-------------|-----------|
| 項目1 | | | |
| 項目2 | | | |
| 項目3 | | | |

**使い方**: まず理想状態を具体的に描き、次に現状を正直に書き出す。両者の差分がそのまま課題になる。理想は「定量的な指標」を含めると差分が明確になる。現状は希望的観測を排し、データや事実に基づいて記述する。

**記入例**（ECサイトの月間売上改善）:
| 項目 | As is（現状） | To be（理想） | Gap（差分） |
|------|-------------|-------------|-----------|
| 月間売上 | 800万円 | 1,500万円 | +700万円（87.5%増） |
| CVR | 1.2% | 2.5% | +1.3pt |
| 平均客単価 | 3,200円 | 4,500円 | +1,300円 |
| リピート率 | 15% | 35% | +20pt |
| カート離脱率 | 72% | 45% | -27pt |

**よくある失敗**:
- **理想が曖昧**: 「売上を増やしたい」ではなく「月間1,500万円」のように定量化する。定量化できない項目も「状態」として具体的に記述する（例: 「問い合わせ対応が属人化していない状態」）
- **現状の美化**: 社内向けプレゼンの癖で現状を良く見せてしまう。第三者が検証できるデータを使う
- **Gapの放置**: 差分を出して満足してしまい、優先順位付けや施策検討に進まない

**活用のヒント**:
- 項目は3〜7個に絞る。多すぎると焦点がぼやける
- To beの期限を明記する（例: 「2025年Q3末時点で」）
- Gapが大きい項目から着手するとは限らない。実現可能性とインパクトの両面で優先度を判断する
- 定性的な項目（例: 組織文化、顧客満足度）も含めてバランスを取る

**次のステップ**:
- Gapの原因を深掘りする → **なぜなぜ分析（05 Whys）** や **特性要因図** を活用
- 施策の優先順位付け → **緊急度／重要度マトリクス** で整理
- 市場環境を踏まえた理想設定 → `/market` スキルの **PEST分析** や **3C分析** を活用
- 具体的な戦略立案 → `/strategy` スキルへ移行

## 02. 6W2H
**目的**: 課題や企画を多角的に分解し、抜け漏れなく定義する

**テンプレート**:
- **What**（何を）:
- **Why**（なぜ）:
- **Who**（誰が）:
- **Whom**（誰に）:
- **When**（いつ）:
- **Where**（どこで）:
- **How**（どのように）:
- **How much**（いくらで）:

**使い方**: 曖昧な課題を8つの切り口で分解する。すべてを埋める必要はなく、空欄が「情報不足の箇所」として可視化される。特に企画書作成や新規プロジェクト立ち上げ時に、関係者間の認識齟齬を防ぐために有効。

**記入例**（社内DX推進プロジェクト）:
- **What**（何を）: 営業部門の顧客管理をExcelからCRM（Salesforce）へ移行する
- **Why**（なぜ）: 顧客情報が属人化しており、担当者の異動・退職時に引き継ぎが困難。また営業活動の可視化ができず、マネジメントが勘に頼っている
- **Who**（誰が）: DX推進室（リーダー: 田中）+ 営業部から選抜メンバー3名 + IT部門2名
- **Whom**（誰に）: 営業部全員（50名）が直接利用者。経営層がダッシュボードで閲覧
- **When**（いつ）: 2025年4月〜9月（6ヶ月）。パイロット運用は7月から第1営業課で開始
- **Where**（どこで）: 東京本社を先行導入、大阪・名古屋支店は第2フェーズ
- **How**（どのように）: Salesforce Sales Cloudを導入。既存Excel顧客データをETLで移行。週1回の研修を2ヶ月間実施
- **How much**（いくらで）: 初期導入費800万円 + 年間ライセンス費600万円。ROI目標: 2年で投資回収

**よくある失敗**:
- **WhyとWhatの混同**: 「売上を上げる（What）」と「市場シェアが低下しているから（Why）」を区別する
- **Whomの不在**: 施策の対象者・受益者が曖昧なまま進めてしまう。特にBtoBでは「意思決定者」と「利用者」を分けて考える
- **How muchの過小評価**: 直接費用だけでなく、人件費・教育コスト・機会損失も含める

**活用のヒント**:
- まずWhyから始めると、プロジェクトの本質的な目的がブレない
- 埋められない項目は「調査が必要な領域」として明示し、担当者とデッドラインを決める
- 複数ステークホルダーがいる場合、各自に個別に6W2Hを埋めてもらい、認識のズレを発見する
- 定期的に（月次など）更新し、計画と実態の乖離を追跡する

**次のステップ**:
- 6W2Hで洗い出した課題の構造化 → **ロジックツリー** で分解
- プロジェクト計画の具体化 → `/execution` スキルの **WBS** や **ガントチャート** を活用
- ターゲット顧客の深掘り → `/customer` スキルの **ペルソナ分析** を活用
- コミュニケーション計画 → `/communication` スキルを活用

## 03. なぜなぜ分析（5 Whys）
**目的**: 表面的な問題から根本原因にたどり着く

**テンプレート**:
```
問題: _______________
なぜ1: _______________
  なぜ2: _______________
    なぜ3: _______________
      なぜ4: _______________
        なぜ5: _______________
→ 根本原因: _______________
→ 対策案: _______________
```

**使い方**: 「なぜ？」を最低5回繰り返す。途中で分岐する場合はロジックツリーと併用する。各段階の回答は「事実」に基づくこと。推測で進めると誤った根本原因に到達する。

**記入例**（ECサイトの売上低下）:
```
問題: 先月のECサイト売上が前月比20%減少した
なぜ1: 購入完了数が大幅に減少したから
  なぜ2: カート投入後の離脱率が72%→85%に上昇したから
    なぜ3: 決済画面でエラーが頻発していたから
      なぜ4: 決済代行会社のAPI仕様変更に対応できていなかったから
        なぜ5: API変更の通知メールを担当者が見落としており、テスト環境での検証も行われていなかったから
→ 根本原因: 外部サービスの仕様変更を検知・対応するプロセスが存在しない
→ 対策案: (1) 外部API変更通知の共有チャンネル設置 (2) 月次の外部サービス変更チェックリスト導入 (3) ステージング環境での定期自動テスト構築
```

**よくある失敗**:
- **「人のせい」で止まる**: 「担当者が怠慢だから」は根本原因ではない。「なぜ怠慢になる仕組みか？」と構造・プロセスの問題まで掘り下げる
- **因果関係の飛躍**: 「なぜ1→なぜ2」の間に論理の飛躍がないか毎回検証する。第三者に説明して違和感がないか確認する
- **5回で無理に止める**: 5回は目安。3回で根本原因に達することもあれば、7回必要なこともある。「これ以上掘り下げても対策が変わらない」地点が終点

**活用のヒント**:
- 分岐が発生したら、それぞれの枝を独立して追跡する（ロジックツリー形式に展開）
- 各「なぜ」の回答に対して「本当にそうか？データはあるか？」と自問する
- 根本原因は「仕組み・プロセス・構造」のレベルに到達させる。個人の能力や意欲に帰結させない
- 対策案は根本原因に直接対応するものにする。表面的な対症療法と構造的対策を区別する

**次のステップ**:
- 根本原因が複数ある場合 → **特性要因図** で体系的に整理
- 対策の優先順位付け → **緊急度／重要度マトリクス** または **意思決定マトリクス** を活用
- 対策の実行計画 → `/execution` スキルで具体化
- 再発防止の仕組み化 → `/improvement` スキルの **PDCA** や **KPT** を活用

## 04. 特性要因図（フィッシュボーンダイアグラム）
**目的**: 問題の原因を体系的に洗い出す

**テンプレート**:
```
            原因カテゴリA ──┐
            原因カテゴリB ──┤
問題 ◀━━━━━━━━━━━━━━━━━━━━┤
            原因カテゴリC ──┤
            原因カテゴリD ──┘
```
主要カテゴリ例（製造業の4M+2）: 人（Man）、方法（Method）、材料（Material）、機械（Machine）、測定（Measurement）、環境（Environment）
主要カテゴリ例（サービス業の4P）: 方針（Policy）、手順（Procedure）、人（People）、設備（Plant）

**使い方**: まず結果（問題）を右端に置き、大骨→中骨→小骨の順で原因を分解していく。ブレインストーミング的に出した後、データで検証して真因を特定する。

**記入例**（顧客満足度低下の原因分析）:
```
        人（Man）─────────────────────────┐
        ├ 新人比率が40%に増加              │
        ├ ベテランの離職が続いている        │
        └ 研修期間が2週間→1週間に短縮      │
                                          │
        方法（Method）───────────────────┤
        ├ マニュアルが3年前から未更新        │
        ├ エスカレーション基準が曖昧         │
        └ 顧客フィードバックの共有が不定期   │
                                          │
顧客満足度が前年比15pt低下 ◀━━━━━━━━━━━━━┤
                                          │
        機械（Machine）──────────────────┤
        ├ CRMの応答速度が遅い              │
        ├ チャットボットの回答精度が低い     │
        └ 電話システムの待ち時間が長い       │
                                          │
        環境（Environment）──────────────┘
        ├ リモートワークでOJTが困難
        ├ 問い合わせ件数が季節要因で150%増
        └ 競合サービスの品質向上で期待値上昇
```

**よくある失敗**:
- **カテゴリの選択ミス**: 製造業の4Mをそのままサービス業に適用してしまう。業種に合ったカテゴリを選ぶ
- **大骨だけで止まる**: 「人の問題」で終わらず、中骨・小骨まで具体化する。具体的なアクションが見えるレベルまで分解する
- **検証なしの原因確定**: 洗い出した原因はあくまで「仮説」。データや現場確認で裏付けを取る

**活用のヒント**:
- 関係者を集めてホワイトボードで作成すると、多角的な視点が得られる
- 各原因に「影響度: 大/中/小」「確信度: 高/中/低」を付記すると優先順位が明確になる
- 原因間の相互関係（例: 「人の問題」と「方法の問題」が連動している）にも注目する
- 完成後、最もインパクトの大きい原因3つに絞って対策を検討する

**次のステップ**:
- 特定した真因の深掘り → **なぜなぜ分析** で根本まで到達
- 原因の構造化 → **ロジックツリー** でMECEに整理
- 対策の検討 → `/idea` スキルの **ブレインストーミング** や **SCAMPER** を活用
- 改善活動の管理 → `/improvement` スキルの **PDCA** を活用

## 05. ロジックツリー
**目的**: 問題や論点をMECEに分解して構造化する

**テンプレート**:
```
テーマ
├── 大分類A
│   ├── 中分類A-1
│   └── 中分類A-2
├── 大分類B
│   ├── 中分類B-1
│   └── 中分類B-2
└── 大分類C
    ├── 中分類C-1
    └── 中分類C-2
```

**種類**: 
- **Whatツリー（要素分解）**: 全体を構成要素に分解する（例: 売上 = 客数 x 客単価）
- **Whyツリー（原因追究）**: 問題の原因を網羅的に洗い出す
- **Howツリー（問題解決）**: 解決策を具体的なアクションまで分解する

**記入例**（SaaSサービスの月間売上分解 - Whatツリー）:
```
月間売上（MRR）: 5,000万円
├── 新規MRR: 800万円
│   ├── インバウンド経由: 500万円
│   │   ├── SEO/コンテンツ: 200万円
│   │   ├── Web広告: 200万円
│   │   └── SNS/紹介: 100万円
│   └── アウトバウンド経由: 300万円
│       ├── テレアポ: 100万円
│       ├── 展示会/セミナー: 150万円
│       └── パートナー紹介: 50万円
├── 既存拡大MRR: 400万円
│   ├── アップセル: 250万円
│   └── クロスセル: 150万円
├── 既存継続MRR: 4,200万円
└── チャーンMRR: ▲400万円（解約）
    ├── 自発的解約: ▲300万円
    │   ├── 競合乗り換え: ▲120万円
    │   ├── 予算削減: ▲100万円
    │   └── 活用不足: ▲80万円
    └── 非自発的解約: ▲100万円
        └── 決済失敗/倒産: ▲100万円
```

**よくある失敗**:
- **MECEでない分解**: 各階層で「漏れ」や「ダブり」がないか確認する。不安なら既知のフレームワーク（3C、4P等）を切り口に使う
- **分解の深さが不均一**: ある枝だけ深く掘り下げ、他が浅いとバランスを欠く。全体を均等に2〜3階層まで展開してから、重要な枝を深掘りする
- **分解して終わり**: ツリーは思考の道具。分解後に「どの枝にレバレッジがあるか」を判断し、アクションに繋げる

**活用のヒント**:
- 第1階層の切り口が最も重要。ここが間違うと全体がズレる
- 数値化できるWhatツリーは、ボトルネック発見に極めて有効（どの枝のインパクトが大きいか一目でわかる）
- Whyツリーは「なぜなぜ分析」を横に展開したもの。複数原因の並列探索に適している
- Howツリーは施策検討に使う。最下層が「明日から実行できるアクション」になるまで分解する

**次のステップ**:
- 各枝の検証 → **イシューツリー** で仮説と検証方法を設定
- ボトルネックの特定 → As is/To beで現状と理想のGapを数値化
- 解決策の評価 → **意思決定マトリクス** で比較
- 戦略への昇華 → `/strategy` スキルで全体方針を策定

## 06. MECE
**目的**: 漏れなく・ダブりなく要素を洗い出す思考フレーム

**チェックリスト**:
- [ ] 全体集合を定義したか？
- [ ] 各要素に重複はないか？（Mutually Exclusive）
- [ ] 全体を網羅しているか？（Collectively Exhaustive）
- [ ] 切り口は適切か？（対立軸、プロセス、構成要素など）
- [ ] 切り口は目的に合っているか？（分析目的によって最適な切り口は異なる）

**代表的な切り口例**: 時系列、プロセス順、対立概念、3C/4P等の既存フレーム、地理的区分、顧客セグメント

**記入例**（飲食チェーンの売上低迷分析 - MECE分解の切り口検討）:

**切り口1: 時間軸** (MECE)
| 朝（6-11時） | 昼（11-14時） | 午後（14-17時） | 夜（17-22時） |
|---|---|---|---|
| 売上比率: 5% | 売上比率: 40% | 売上比率: 15% | 売上比率: 40% |
| → 未活用 | → 安定 | → 低稼働 | → 低下傾向 |

**切り口2: 顧客タイプ** (MECE)
| 新規顧客 | リピーター（月1-3回） | ヘビーユーザー（週1以上） |
|---|---|---|
| 30% | 45% | 25% |
| → 横ばい | → 微減 | → 大幅減 |

**切り口3: 収益構造** (MECE)
- 売上 = 客数 x 客単価
- 客数 = 席数 x 回転率 x 営業日数
- 客単価 = フード単価 + ドリンク単価 + サイドメニュー

**よくある失敗**:
- **完璧主義に陥る**: 実務では「概ねMECE」で十分。厳密さを追求しすぎて時間を浪費しない
- **切り口の多重適用**: 同時に複数の切り口を混在させる（例: 「若者」「東京」「リピーター」を同列に並べる）。一つの階層には一つの切り口を適用する
- **「その他」の乱用**: 「その他」カテゴリが全体の30%以上を占める場合、切り口自体を見直す

**活用のヒント**:
- MECEは「型」であり、他のすべてのフレームワークの基盤。ロジックツリー、特性要因図、イシューツリーはすべてMECEを前提としている
- 既存のフレームワーク（3C、4P、バリューチェーンなど）はMECEが検証済みの「既製品」。自分で切り口を考える前にまず適用を検討する
- 「本当にこれで全部か？」と問い続ける習慣が重要。チームメンバーに確認してもらうのも有効
- 分析の目的に応じて切り口を選ぶ。同じテーマでも目的が違えば最適な切り口も変わる

**次のステップ**:
- MECE分解の実践 → **ロジックツリー** で構造化
- 既存フレームワークの活用 → `/market` スキルの **3C分析** や **4P分析**、`/strategy` スキルの **SWOT分析** を活用
- 顧客セグメントの深掘り → `/customer` スキルを活用

## 07. 緊急度／重要度マトリクス
**目的**: タスクや課題の優先順位を4象限で整理する

**テンプレート**:
|  | 重要度：高 | 重要度：低 |
|---|---------|---------|
| **緊急度：高** | 第1象限：即実行 | 第3象限：委任・効率化 |
| **緊急度：低** | 第2象限：計画的に取組む | 第4象限：削減・排除 |

**使い方**: 第2象限（重要だが緊急でない）に時間を使えているかが生産性の鍵。第1象限に追われている場合、第2象限の不足が原因であることが多い。

**記入例**（スタートアップCTOの四半期タスク整理）:

| | 重要度：高 | 重要度：低 |
|---|---------|---------|
| **緊急度：高** | **即実行**: 本番サーバー障害対応 / セキュリティ脆弱性パッチ適用 / 大口顧客からのバグ報告対応 / 採用面接（候補者の他社選考期限迫る） | **委任・効率化**: 社内ツールの軽微なバグ修正 / 定例MTGの議事録作成 / 経費精算 / 問い合わせ一次対応 |
| **緊急度：低** | **計画的に取組む**: 技術的負債の解消 / CI/CDパイプライン改善 / チームメンバーの1on1・育成 / セキュリティ監査体制の構築 / 中長期アーキテクチャ設計 | **削減・排除**: 惰性で続けている週次レポート / 参加意義の薄い社外勉強会 / 過剰な社内チャット対応 / 不要な承認フロー |

**よくある失敗**:
- **すべてが「緊急かつ重要」になる**: 基準を明確にする。「今週中に対応しないと具体的な損失が発生するか？」で緊急度を判定。「半年後の目標達成に直結するか？」で重要度を判定
- **第2象限を後回しにし続ける**: 第2象限のタスクにはカレンダーに具体的な時間枠を確保する。週の20%以上を第2象限に充てることを目標にする
- **一度分類して更新しない**: 状況は変化する。週次または隔週で見直す

**活用のヒント**:
- 各象限に入れるタスクは5〜7個程度に絞る。多すぎる場合はさらに細分化して別のマトリクスを作る
- チームで実施する場合、「重要度」「緊急度」の定義を事前に合意する
- 第4象限のタスクは勇気を持って「やらない」と決める。削減した時間を第2象限に振り替える
- 第3象限は「自分がやらなくてもよいタスク」。委任先（メンバー、外注、ツール自動化）を具体的に決める

**次のステップ**:
- 第1象限の課題の根本原因 → **なぜなぜ分析** で構造的問題を特定（第2象限の不足が原因かもしれない）
- 第2象限の計画策定 → `/execution` スキルで実行計画を作成
- チームへの委任設計 → `/organization` スキルの **RACI** を活用
- 業務改善 → `/improvement` スキルの **業務フロー分析** を活用

## 08. 意思決定マトリクス
**目的**: 複数の選択肢を定量的に評価して最善策を選ぶ

**テンプレート**:
| 評価基準 | 重み | 選択肢A | 選択肢B | 選択肢C |
|---------|-----|--------|--------|--------|
| 基準1 | x○ | 点数 | 点数 | 点数 |
| 基準2 | x○ | 点数 | 点数 | 点数 |
| 基準3 | x○ | 点数 | 点数 | 点数 |
| **加重合計** | | **○点** | **○点** | **○点** |

**使い方**: 評価基準と重みを先に決め、その後に各選択肢を採点する。感覚的な判断を構造化できる。基準と重みは選択肢を見る前に設定することで、確証バイアスを防ぐ。

**記入例**（プロジェクト管理ツールの選定）:
| 評価基準 | 重み | Jira | Asana | Linear |
|---------|------|------|-------|--------|
| 開発チームとの親和性 | x5 | 5 (=25) | 3 (=15) | 5 (=25) |
| カスタマイズ性 | x4 | 5 (=20) | 3 (=12) | 4 (=16) |
| 学習コストの低さ | x3 | 2 (=6) | 4 (=12) | 4 (=12) |
| 他ツール連携 | x3 | 5 (=15) | 4 (=12) | 3 (=9) |
| コスト（年間） | x3 | 3 (=9) | 4 (=12) | 4 (=12) |
| UI/UXの快適さ | x2 | 2 (=4) | 4 (=8) | 5 (=10) |
| サポート品質 | x1 | 4 (=4) | 3 (=3) | 3 (=3) |
| **加重合計** | | **83点** | **74点** | **87点** |

→ 定量評価ではLinearが最高スコア。ただし「他ツール連携」でJiraに大きく劣るため、既存ツール環境との整合性を追加検証の上、最終判断する。

**よくある失敗**:
- **結論ありきで基準を設定する**: 特定の選択肢が有利になるよう、無意識に基準や重みを操作してしまう。基準設定は選択肢の詳細を検討する前に行う
- **基準が多すぎる**: 7つ以下に絞る。多すぎると各基準の重みが薄まり、結局すべてが同じスコアに収束する
- **定量結果を盲信する**: マトリクスは「議論の土台」であり「最終結論」ではない。スコアが僅差の場合は定性的な判断も加味する

**活用のヒント**:
- 採点は1〜5点の5段階が扱いやすい。10段階だと基準が曖昧になる
- 重みは1〜5で設定し、合計が20前後になるようにすると各基準のバランスが取りやすい
- 複数人で採点し、スコアが大きくズレる基準について議論すると、認識の齟齬が可視化される
- 「致命的な基準」（例: セキュリティ要件を満たさない）は点数評価ではなく足切り条件として先に適用する

**次のステップ**:
- 選択肢の洗い出し → **ロジックツリー（Howツリー）** でMECEに列挙
- 評価基準の妥当性検証 → ステークホルダーへのヒアリング → `/communication` スキルを活用
- 選定後の実行計画 → `/execution` スキルで具体化
- 選択肢のアイデア創出 → `/idea` スキルの **ブレインストーミング** を活用

## 09. イシューツリー
**目的**: 解くべき問い（イシュー）を分解し、検証可能なサブイシューに落とし込む

**テンプレート**:
```
メインイシュー: ________________？
├── サブイシュー1: ____________？
│   ├── 仮説:
│   ├── 検証方法:
│   └── 必要データ:
├── サブイシュー2: ____________？
│   ├── 仮説:
│   ├── 検証方法:
│   └── 必要データ:
└── サブイシュー3: ____________？
    ├── 仮説:
    ├── 検証方法:
    └── 必要データ:
```

**使い方**: ロジックツリーと異なり、各ノードが「問い」の形になる。仮説駆動で分析を進める際に有効。コンサルティングプロジェクトの初期設計で頻繁に使われる。

**記入例**（D2Cブランドの成長戦略検討）:
```
メインイシュー: 当社D2Cブランドは3年で売上10億円を達成できるか？
│
├── サブイシュー1: 十分な市場規模が存在するか？
│   ├── 仮説: ターゲット市場は年間500億円規模で、年率8%成長している
│   ├── 検証方法: 業界レポート分析、競合売上推計、TAM/SAM/SOM算出
│   └── 必要データ: 矢野経済研究所レポート、上場競合のIR資料、Google Trends
│
├── サブイシュー2: 競合に対して持続可能な差別化要因があるか？
│   ├── 仮説: 独自原料の調達ルートと、D2Cによる顧客データ活用が差別化になる
│   ├── 検証方法: 競合製品比較、顧客インタビュー（n=30）、ブラインドテスト
│   └── 必要データ: 競合製品サンプル、既存顧客NPS、成分分析結果
│
├── サブイシュー3: 必要な顧客獲得コスト（CAC）で採算が取れるか？
│   ├── 仮説: CACを8,000円以下に抑えれば、LTV/CAC比率3倍以上を維持できる
│   ├── 検証方法: テストマーケティング（3ヶ月）、コホート分析、LTVモデル構築
│   └── 必要データ: 広告運用実績、リピート率推移、解約率、客単価推移
│
└── サブイシュー4: 実行に必要なリソース（人材・資金）を確保できるか？
    ├── 仮説: マーケティング人材2名の追加採用と、運転資金1.5億円の調達が必要
    ├── 検証方法: 組織計画策定、資金調達シナリオ分析、VCヒアリング
    └── 必要データ: 人材市場の採用難易度、類似企業の調達事例、自社BS/PL予測
```

**よくある失敗**:
- **問いの形になっていない**: 「市場分析」ではなく「十分な市場規模が存在するか？」のようにYes/Noまたは定量的に回答可能な問いにする
- **サブイシューがMECEでない**: メインイシューに対してサブイシューが網羅的かを確認する。「これらのサブイシューすべてにYesと答えられたら、メインイシューもYesと言えるか？」と自問する
- **検証不可能な仮説**: 「当社の製品は優れている」ではなく、「ブラインドテストで既存品より評価が高い」のように検証可能な形にする

**活用のヒント**:
- メインイシューの設定が最も重要。「正しい問い」を立てれば、分析の半分は終わったも同然
- 仮説は「間違っていても良い」。仮説があることで検証の方向性が定まり、効率的に情報収集できる
- 各サブイシューに「担当者」と「デッドライン」を設定すると、プロジェクト管理ツールとしても機能する
- 検証結果が仮説と異なった場合、イシューツリー自体を更新する。生きたドキュメントとして扱う

**次のステップ**:
- 市場関連のサブイシュー検証 → `/market` スキルの **PEST分析**、**5Forces分析** を活用
- 戦略立案 → `/strategy` スキルの **SWOT分析** や **アンゾフマトリクス** を活用
- 顧客関連のサブイシュー検証 → `/customer` スキルの **カスタマージャーニー** を活用
- 実行計画 → `/execution` スキルで検証スケジュールとマイルストーンを設定

## 対話の進め方

### ステップ1: 状況のヒアリング

ユーザーの状況を正確に把握するため、以下の観点でAskUserQuestionを活用する。

**初回ヒアリングの質問例**:

- 「現在、どのような問題や課題に直面されていますか？できるだけ具体的に教えてください（例: 売上低下、業務効率の悪化、新規事業の方向性が定まらない、など）」
- 「その問題は、いつ頃から発生していますか？また、きっかけとなる出来事はありましたか？」
- 「この問題に取り組む目的は何ですか？（例: 経営会議での報告、チームの改善活動、個人の業務改善など）」
- 「現時点で、原因や解決策について何か仮説をお持ちですか？」
- 「この分析に使える時間はどの程度ですか？（例: 今すぐ概要が欲しい、1週間かけてじっくり分析したい）」

### ステップ2: フレームワークの提案

ヒアリング結果に基づき、最適なフレームワークを1〜2個提案する。選定理由を明確に伝える。

**提案時のガイドライン**:

| ユーザーの状況 | 推奨フレームワーク | 理由 |
|---|---|---|
| 「何が問題かわからない」 | As is/To be → ロジックツリー | まず理想と現状のGapを可視化し、構造的に分解 |
| 「問題はわかっているが原因がわからない」 | なぜなぜ分析 or 特性要因図 | 単一原因なら5Whys、複数原因が疑われるならフィッシュボーン |
| 「原因はわかっているが何から手をつけるべきか迷う」 | 緊急度/重要度マトリクス | 優先順位の明確化 |
| 「複数の解決策があり選べない」 | 意思決定マトリクス | 定量的な比較評価 |
| 「企画の全体像を整理したい」 | 6W2H | 8つの切り口で網羅的に定義 |
| 「仮説はあるが検証の進め方がわからない」 | イシューツリー | 仮説駆動の分析設計 |
| 「分析の抜け漏れが心配」 | MECE → ロジックツリー | 思考の網羅性を担保 |

### ステップ3: 対話的なワークシート作成

テンプレートを提示し、項目ごとにユーザーと対話しながら埋めていく。

**対話中の質問例**:

- 「この項目について、具体的な数値やデータはお持ちですか？」
- 「『売上低下』とのことですが、具体的にはどの期間で何%の低下ですか？」
- 「この原因について、他に考えられる要因はありませんか？」
- 「チームメンバーや上司は、この問題についてどのような認識をお持ちですか？」
- 「過去に同様の問題に取り組んだことはありますか？その時はどのように対処しましたか？」
- 「この分析結果は、誰に対してどのような形で報告する予定ですか？」

### ステップ4: ワークシートの完成と出力

完成したワークシートをMarkdown形式で整理して出力する。以下を含める:
- 分析の前提条件と対象範囲
- フレームワークの結果
- 主要な発見事項（Key Findings）を3〜5個
- 残課題や追加調査が必要な点

### ステップ5: 次のステップの提案

分析結果に基づき、次に取り組むべきアクションを提案する。

**提案の観点**:
- 同じproblemスキル内の別フレームワークで深掘りする必要があるか
- `/strategy` スキルで戦略立案に進むべきか
- `/market` スキルで外部環境分析が必要か
- `/customer` スキルで顧客理解を深めるべきか
- `/execution` スキルで実行計画に落とし込むべきか
- `/improvement` スキルで改善サイクルを回すべきか
- `/idea` スキルでアイデア創出が必要か
- `/organization` スキルで組織設計の検討が必要か
- `/communication` スキルでステークホルダーへの伝え方を検討すべきか
