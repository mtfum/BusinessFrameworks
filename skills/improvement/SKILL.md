# 業務改善・プロセス最適化フレームワーク

ユーザーの $ARGUMENTS に基づき、以下のフレームワークから適切なものを適用してください。

---

## 01. PDCA
**目的**: 計画→実行→評価→改善のサイクルを回して継続的に改善する
**テンプレート**:
| フェーズ | 内容 | 詳細 |
|---------|------|------|
| **Plan**（計画） | 目標と計画を立てる | 目標: / 施策: / スケジュール: |
| **Do**（実行） | 計画を実行する | 実施内容: / 記録: |
| **Check**（評価） | 結果を測定・評価する | 目標vs実績: / 差分の原因: |
| **Act**（改善） | 改善策を次のPlanに反映 | 継続すること: / 改善すること: / やめること: |

**使い方**: 1サイクルの期間を決めてから始める（週次・月次・四半期など）。Checkを飛ばさないことが重要。

---

## 02. KPT
**目的**: 振り返りをKeep・Problem・Tryの3つで構造化する
**テンプレート**:
| 区分 | 内容 |
|------|-----|
| **Keep**（続けること） | ・ |
| **Problem**（問題・課題） | ・ |
| **Try**（次に試すこと） | ・ |

**使い方**: まずKeepから書き出す（ポジティブ先行）。ProblemからTryへの変換を具体的にする。チームの定例振り返りに最適。

---

## 03. YWT
**目的**: 「やったこと」から学びを抽出し、次のアクションにつなげる振り返り手法
**テンプレート**:
| 区分 | 内容 |
|------|-----|
| **Y**（やったこと） | ・ |
| **W**（わかったこと） | ・ |
| **T**（次にやること） | ・ |

**使い方**: KPTとの違いは「問題」ではなく「わかったこと（学び）」に焦点を当てること。個人の振り返り日記にも向いている。

---

## 04. 業務フロー図
**目的**: 業務プロセスの流れを図示し、ボトルネックや無駄を可視化する
**テンプレート**:
```
[開始] → (判断?) ─Yes→ [処理A] → [処理B] → [終了]
                  │
                  No
                  ↓
              [処理C] → [処理B] → [終了]
```

**記号**:
- `[ ]` = 処理・作業
- `( )` = 判断・分岐
- `→` = 流れ
- `[開始/終了]` = 端子

**使い方**: まず現状（As is）のフローを描き、次に理想（To be）のフローを描いて比較する。

## 05. PERT図
**目的**: タスクの依存関係と所要時間からクリティカルパス（最長経路）を特定する
**テンプレート**:
| タスク | 先行タスク | 楽観値(a) | 最頻値(m) | 悲観値(b) | 期待値 |
|-------|----------|----------|----------|----------|-------|
| A | - | | | | (a+4m+b)/6 |
| B | A | | | | |
| C | A | | | | |
| D | B, C | | | | |

**クリティカルパス**: 最も時間がかかる経路 = 

**使い方**: クリティカルパス上のタスクが遅延すると全体が遅延する。ここにリソースを集中させる。

## 06. RACI
**目的**: タスクごとの役割分担を4種類の責任で明確にする
**テンプレート**:
| タスク | 担当者A | 担当者B | 担当者C | 担当者D |
|-------|--------|--------|--------|--------|
| タスク1 | R | A | C | I |
| タスク2 | I | R | A | C |
| タスク3 | C | I | R | A |

**役割定義**:
- **R**esponsible（実行責任者）: 実際に作業する人
- **A**ccountable（説明責任者）: 最終的な意思決定者（各タスク1人のみ）
- **C**onsulted（相談先）: 事前に意見を求める人
- **I**nformed（報告先）: 事後に結果を知らせる人

---

## 07. ムリ・ムダ・ムラ（ダラリの法則）
**目的**: 業務の非効率を3つの視点で洗い出す
**テンプレート**:
| 視点 | 定義 | 該当する業務 | 改善策 |
|------|------|------------|-------|
| **ムリ**（無理） | 能力以上の負荷がかかっている | | |
| **ムダ**（無駄） | 価値を生まない作業 | | |
| **ムラ**（斑） | 品質や量のばらつき | | |

**使い方**: まず現場の業務を一覧化し、各業務に「ムリ・ムダ・ムラ」のラベルを付ける。

---

## 08. ECRS
**目的**: 業務改善を4つの原則で検討する（効果の大きい順）
**テンプレート**:
| 原則 | 問い | 対象業務 | 改善策 |
|------|-----|---------|-------|
| **E**liminate（排除） | やめられないか？ | | |
| **C**ombine（結合） | まとめられないか？ | | |
| **R**earrange（交換） | 順序や場所を変えられないか？ | | |
| **S**implify（簡素化） | もっと簡単にできないか？ | | |

**使い方**: E→C→R→Sの順で検討する。Eliminateが最も効果が大きい（やめるのが最大の改善）。

---

## 対話の進め方

1. AskUserQuestionで改善したい業務・プロセスをヒアリング
2. 最適なフレームワークを提案
3. 対話的にテンプレートを埋めていく
4. 完成したワークシートをMarkdownで出力
