# 業務改善・プロセス最適化フレームワーク

ユーザーの $ARGUMENTS に基づき、以下のフレームワークから適切なものを適用してください。

---

## 01. PDCA
**目的**: 計画→実行→評価→改善のサイクルを回して継続的に改善する

**いつ使うか**: 明確な目標があり、反復的に改善していきたいとき。定量的な指標で進捗を測れるテーマに特に有効。

**テンプレート**:
| フェーズ | 内容 | 詳細 |
|---------|------|------|
| **Plan**（計画） | 目標と計画を立てる | 目標: / 施策: / スケジュール: / 成功指標（KPI）: |
| **Do**（実行） | 計画を実行する | 実施内容: / 記録: / 想定外の出来事: |
| **Check**（評価） | 結果を測定・評価する | 目標vs実績: / 差分の原因: / データの根拠: |
| **Act**（改善） | 改善策を次のPlanに反映 | 継続すること: / 改善すること: / やめること: / 次サイクルの仮説: |

**使い方**: 1サイクルの期間を決めてから始める（週次・月次・四半期など）。Checkを飛ばさないことが重要。

### 記入例（営業チームの成約率改善）

| フェーズ | 内容 | 詳細 |
|---------|------|------|
| **Plan** | 成約率を20%→30%に引き上げる | 目標: 成約率30%（3ヶ月後） / 施策: 商談前のヒアリングシートを導入し、顧客課題の事前把握を徹底する / スケジュール: 1ヶ月目=シート設計・テスト、2ヶ月目=全員運用、3ヶ月目=効果測定 / KPI: ヒアリングシート記入率100%、成約率30% |
| **Do** | ヒアリングシートを全商談で活用 | 実施内容: 全15名の営業担当にシートを配布し研修を実施。42件の商談で使用 / 記録: 記入率は85%にとどまった / 想定外: ベテラン営業から「面倒」との声が多く、記入が形骸化した案件があった |
| **Check** | 成約率25%（目標未達だが改善） | 目標vs実績: 30%目標に対し25%（+5pt改善） / 差分の原因: シート活用した商談の成約率は33%だったが、未活用商談が18%のまま。活用率の低さがボトルネック / データ: シート活用42件中14件成約、未活用18件中3件成約 |
| **Act** | 活用率向上にフォーカスした次サイクルへ | 継続: ヒアリングシート自体は効果あり、継続 / 改善: シートの記入項目を10→5に簡素化。SFAに組み込んで入力負荷を下げる / やめる: 紙ベースの運用 / 次サイクルの仮説: 記入負荷を半減すれば活用率95%以上になり、成約率30%を達成できる |

### よくある失敗
1. **Planに時間をかけすぎる**: 完璧な計画を求めて実行に移れない。まず小さく始めてサイクルを回すことが重要
2. **Checkをスキップする**: 「忙しいから」と評価を省略すると、ただの繰り返しになりPDCAではなくなる。定量データを必ず取る
3. **Actが精神論になる**: 「もっと頑張る」は改善策ではない。具体的に何を変えるか、行動レベルで記述する

### 活用のヒント
- 1サイクルは短めに設定する（最初は2週間程度がおすすめ）。長すぎるとCheckまでの距離が遠くなる
- Planの段階で「何をもってCheck（成功/失敗の判断）とするか」を明確にしておく
- PDCAノートやスプレッドシートにサイクルごとの記録を残し、サイクル間の変化を追えるようにする
- 小さなPDCAを回してから大きなPDCAに拡大するのが定石

### 次のステップ
- 目標設定を精緻にしたい → `/execution`（OKR、SMARTゴールなど）
- 問題の根本原因を深掘りしたい → `/problem`（なぜなぜ分析、特性要因図など）
- チーム全体の役割分担を明確にしたい → 本スキルの **06. RACI** と組み合わせる

## 02. KPT
**目的**: 振り返りをKeep・Problem・Tryの3つで構造化する

**いつ使うか**: スプリント終了時、プロジェクト完了後、定例ミーティングでの振り返りなど。チームで短時間（30-60分）で実施するのに最適。

**テンプレート**:
| 区分 | 内容 |
|------|-----|
| **Keep**（続けること） | ・ |
| **Problem**（問題・課題） | ・ |
| **Try**（次に試すこと） | ・ |

**使い方**: まずKeepから書き出す（ポジティブ先行）。ProblemからTryへの変換を具体的にする。チームの定例振り返りに最適。

### 記入例（2週間スプリントの振り返り）

| 区分 | 内容 |
|------|-----|
| **Keep** | ・朝会を15分以内に終える運用が定着した。ブロッカーの早期発見に貢献 |
|  | ・ペアプログラミングを導入したことで、コードレビューの手戻りが3割減った |
|  | ・デザイナーとの週次同期ミーティングが機能しており、仕様齟齬がなくなった |
| **Problem** | ・スプリント後半にタスクが集中し、最終日に3つのPRが同時にマージされた |
|  | ・テスト環境のデプロイが手動で、毎回30分かかっている |
|  | ・見積もりが甘く、計画した8ストーリーのうち6つしか完了できなかった |
| **Try** | ・スプリント中間（水曜）にバーンダウンチャートを確認し、遅れがあれば木曜にスコープ調整する |
|  | ・テスト環境のCI/CDパイプラインを構築する（田中さんが来スプリントで着手） |
|  | ・見積もり時にバッファ係数1.3をかける。3スプリント後に係数の妥当性を検証する |

### よくある失敗
1. **Keepが出てこない**: 問題ばかりに目が行くチームは疲弊する。必ずKeepから始め、最低3つは出す。「当たり前にできていること」もKeepに含める
2. **ProblemとTryが1対1対応していない**: すべてのProblemに対してTryがあるか確認する。Tryのない問題は放置されるだけ
3. **Tryが抽象的**: 「コミュニケーションを改善する」ではなく「毎週金曜15時に30分の共有会を設ける」のように、誰が・いつ・何をするかを明記する

### 活用のヒント
- 付箋（物理/デジタル）を使い、全員が同時に書き出してから共有すると、声の大きい人に引きずられない
- 前回のTryの実施状況を最初に確認する。やりっぱなしにしない
- Problemが多すぎるときは投票で優先順位をつけ、上位3つだけTryを考える
- ファシリテーターを毎回交代すると、チーム全員が振り返りのオーナーシップを持てる

### 次のステップ
- 個人の学びを深掘りしたい → 本スキルの **03. YWT** と比較・使い分け
- 問題の原因を構造的に分析したい → `/problem`（ロジックツリー、なぜなぜ分析）
- 改善施策を継続的に回したい → 本スキルの **01. PDCA** のDoに組み込む
- チームの状態を可視化したい → `/organization`（チームマネジメントフレームワーク）

## 03. YWT
**目的**: 「やったこと」から学びを抽出し、次のアクションにつなげる振り返り手法

**いつ使うか**: 個人の日報・週報、研修後の振り返り、新しい取り組みを試した後の学びの整理。KPTと違い「問題」ではなく「学び」にフォーカスするため、ポジティブな振り返りに向いている。

**テンプレート**:
| 区分 | 内容 |
|------|-----|
| **Y**（やったこと） | ・ |
| **W**（わかったこと） | ・ |
| **T**（次にやること） | ・ |

**使い方**: KPTとの違いは「問題」ではなく「わかったこと（学び）」に焦点を当てること。個人の振り返り日記にも向いている。

### 記入例（新規事業の顧客インタビュー実施後）

| 区分 | 内容 |
|------|-----|
| **Y**（やったこと） | ・ターゲット業界（製造業）の中堅企業5社にオンラインインタビューを実施（各60分） |
|  | ・事前に仮説シート（課題仮説3つ）を作成し、インタビューガイドとして使用 |
|  | ・インタビュー後、即日でメモを構造化し、チームに共有した |
| **W**（わかったこと） | ・仮説1「在庫管理が最大の課題」は5社中1社のみ。実際は「部門間の情報共有の遅れ」が共通課題だった |
|  | ・意思決定者（部長クラス）と現場担当者で課題認識が大きく異なる。両方にヒアリングしないと実態が見えない |
|  | ・60分では深掘りが不十分。45分で概要を聞き、2回目の30分で深掘りする2回構成の方が質が高い |
| **T**（次にやること） | ・仮説を「情報共有の遅れ」にピボットし、課題の具体的な発生場面を整理する |
|  | ・次の5社は意思決定者と現場担当者の2名セットでインタビューを依頼する |
|  | ・インタビューを2回構成に変更し、1回目のガイドを来週月曜までに改訂する |

### よくある失敗
1. **Yが行動の羅列になる**: 「会議に出た」だけでなく「会議で○○の提案をした」のように、自分の主体的行動を書く
2. **WがYの繰り返しになる**: 「インタビューをした→インタビューは大事だとわかった」では学びがない。「何が予想と違ったか」「なぜそうなったか」を書く
3. **Tが大きすぎる**: 次の1-2週間で具体的に着手できるアクションに落とし込む

### 活用のヒント
- 日報として毎日書くと、1週間分を集約するだけで質の高い週報になる
- Wは「成功からの学び」と「失敗からの学び」の両方を意識する
- YWTを3ヶ月分振り返ると、自分の成長パターンや繰り返し出てくる課題が見える
- チームで使う場合は、各メンバーのWを共有するだけでもナレッジマネジメントになる

### 次のステップ
- チームでの振り返りに切り替えたい → 本スキルの **02. KPT** を使う
- 学びを体系的に整理したい → `/idea`（マインドマップ的な整理）
- 次のアクションを目標として管理したい → `/execution`（OKR、タスク管理）

## 04. 業務フロー図
**目的**: 業務プロセスの流れを図示し、ボトルネックや無駄を可視化する

**いつ使うか**: 業務の引き継ぎ、プロセス改善の初期段階、部門間の業務連携を整理するとき。「現状（As is）」と「理想（To be）」を比較するために使う。

**テンプレート**:
```
[開始] → (判断?) ─Yes→ [処理A] → [処理B] → [終了]
                  │
                  No
                  ↓
              [処理C] → [処理B] → [終了]
```

**記号**:
- `[ ]` = 処理・作業
- `( )` = 判断・分岐
- `→` = 流れ
- `[開始/終了]` = 端子
- `// //` = 待ち時間・滞留（ボトルネック候補）
- `《 》` = システム・ツール

**使い方**: まず現状（As is）のフローを描き、次に理想（To be）のフローを描いて比較する。

### 記入例（経費精算プロセスの改善）

**As is（現状フロー）**:
```
[申請者: 紙の領収書を整理]
    ↓
[申請者: Excelに金額を入力] ← //平均2日かかる//
    ↓
[申請者: 上長にメールで送付]
    ↓
//上長の確認待ち: 平均3日//
    ↓
(上長: 内容OK?) ─No→ [上長: メールで差し戻し] → [申請者: 修正] → (ループ)
    │
    Yes
    ↓
[上長: 承認印を押して経理に回付]
    ↓
//経理の処理待ち: 平均5日//
    ↓
[経理: システムに手入力]
    ↓
[経理: 振込処理]
    ↓
[終了] ※申請から振込まで平均15営業日
```

**To be（改善後フロー）**:
```
[申請者: 《経費精算アプリ》で領収書を撮影・金額入力]
    ↓
[《システム》: OCRで自動読取・金額チェック]
    ↓
[《システム》: 上長にプッシュ通知]
    ↓
(上長: 《アプリ》で承認?) ─No→ [《アプリ》で差し戻しコメント] → [申請者: 修正] → (ループ)
    │
    Yes
    ↓
[《システム》: 経理システムに自動連携]
    ↓
[経理: 振込処理]
    ↓
[終了] ※申請から振込まで平均3営業日
```

**改善効果**: 15営業日 → 3営業日（80%短縮）。手入力工程2つを自動化、待ち時間を通知で短縮。

### よくある失敗
1. **現状フローを描かずに理想から始める**: 現状の正確な把握なしに改善はできない。必ずAs isから始める
2. **粒度がバラバラ**: 「書類を作成する」と「ハンコを押す」が同じレベルで並ぶと分析しづらい。同程度の粒度で統一する
3. **例外フローを無視する**: 正常系だけ描いて満足しがち。差し戻し・エラー・例外のフローこそ改善のヒントが多い

### 活用のヒント
- 各処理に「所要時間」「担当者」「使用ツール」を書き添えると分析精度が上がる
- 待ち時間（滞留時間）をハイライトする。多くの場合、作業時間より待ち時間の方が長い
- 現場の担当者と一緒に描く。机上で描いたフローと実態は必ずズレがある
- まず付箋で大まかな流れを作り、後から清書する

### 次のステップ
- フロー上のボトルネックの根本原因を探る → `/problem`（なぜなぜ分析、特性要因図）
- ムダな工程を体系的に排除したい → 本スキルの **07. ムリ・ムダ・ムラ** や **08. ECRS**
- 改善プロジェクトのスケジュールを組みたい → 本スキルの **05. PERT図**
- 改善効果を関係者に伝えたい → `/communication`（プレゼンテーションフレームワーク）

## 05. PERT図
**目的**: タスクの依存関係と所要時間からクリティカルパス（最長経路）を特定する

**いつ使うか**: プロジェクト計画の策定、納期の見積もり、リソース配分の最適化。複数タスクが並行・直列で進むプロジェクトに特に有効。

**テンプレート**:
| タスク | 先行タスク | 楽観値(a) | 最頻値(m) | 悲観値(b) | 期待値 |
|-------|----------|----------|----------|----------|-------|
| A | - | | | | (a+4m+b)/6 |
| B | A | | | | |
| C | A | | | | |
| D | B, C | | | | |

**クリティカルパス**: 最も時間がかかる経路 = 

**使い方**: クリティカルパス上のタスクが遅延すると全体が遅延する。ここにリソースを集中させる。

### 記入例（社内システムリプレースプロジェクト）

| タスク | 内容 | 先行タスク | 楽観値(a) | 最頻値(m) | 悲観値(b) | 期待値(日) |
|-------|------|----------|----------|----------|----------|----------|
| A | 要件定義 | - | 10 | 14 | 21 | 14.5 |
| B | UI/UXデザイン | A | 7 | 10 | 15 | 10.3 |
| C | DB設計 | A | 5 | 7 | 12 | 7.5 |
| D | フロントエンド開発 | B | 14 | 21 | 35 | 22.2 |
| E | バックエンド開発 | C | 14 | 21 | 28 | 21.0 |
| F | API結合テスト | D, E | 5 | 7 | 14 | 8.2 |
| G | データ移行 | C | 7 | 10 | 21 | 11.3 |
| H | ユーザー受入テスト | F, G | 7 | 10 | 14 | 10.2 |

**経路分析**:
- 経路1: A→B→D→F→H = 14.5 + 10.3 + 22.2 + 8.2 + 10.2 = **65.4日**（クリティカルパス）
- 経路2: A→C→E→F→H = 14.5 + 7.5 + 21.0 + 8.2 + 10.2 = 61.4日
- 経路3: A→C→G→H = 14.5 + 7.5 + 11.3 + 10.2 = 43.5日

**クリティカルパス**: A→B→D→F→H（65.4日）。UI/UXデザインとフロントエンド開発がボトルネック。

**対策**: フロントエンド開発（D）に追加リソースを配置。デザインの早期FIXを優先する。

### よくある失敗
1. **依存関係の見落とし**: 「実は先にXが終わらないとYに着手できない」という隠れた依存関係を見逃すと、計画が破綻する
2. **楽観値ばかりで見積もる**: 悲観値を軽視すると、現実にはほぼ確実に遅延する。悲観値は「何かが1つうまくいかなかった場合」で見積もる
3. **クリティカルパス以外を軽視する**: クリティカルパスに近い経路（サブクリティカルパス）も注意が必要。少しの遅延でクリティカルパスが入れ替わることがある

### 活用のヒント
- 期待値の計算式 (a+4m+b)/6 は、最頻値に4倍の重みを置くベータ分布近似。直感より信頼できる
- プロジェクト全体の標準偏差も計算すると、「90%の確率でX日以内に完了」といった確率的な見積もりが可能
- クリティカルパス上のタスクにはバッファ（余裕日数）を持たせない代わりに、プロジェクト全体の末尾にプロジェクトバッファを設ける（CCPM的アプローチ）
- 定期的にPERT図を更新し、クリティカルパスの変化を追跡する

### 次のステップ
- タスクの担当者を明確にしたい → 本スキルの **06. RACI**
- プロジェクトの目標設定を精緻化したい → `/execution`（WBS、ガントチャート、OKR）
- リスク要因を洗い出したい → `/problem`（リスクマトリクスなど）

## 06. RACI
**目的**: タスクごとの役割分担を4種類の責任で明確にする

**いつ使うか**: プロジェクト開始時の役割定義、部門横断プロジェクト、「誰がやるのか不明」な業務の整理。責任の所在が曖昧なときに特に有効。

**テンプレート**:
| タスク | 担当者A | 担当者B | 担当者C | 担当者D |
|-------|--------|--------|--------|--------|
| タスク1 | R | A | C | I |
| タスク2 | I | R | A | C |
| タスク3 | C | I | R | A |

**役割定義**:
- **R**esponsible（実行責任者）: 実際に作業する人。複数人でもよい
- **A**ccountable（説明責任者）: 最終的な意思決定者。**各タスクに必ず1人だけ**
- **C**onsulted（相談先）: 事前に意見を求める人（双方向コミュニケーション）
- **I**nformed（報告先）: 事後に結果を知らせる人（一方向コミュニケーション）

### 記入例（新製品ローンチプロジェクト）

| タスク | プロダクトマネージャー | エンジニアリーダー | デザイナー | マーケティング | 法務 | 経営層 |
|-------|-------------------|-----------------|----------|-------------|------|-------|
| 製品仕様策定 | A | C | C | C | I | I |
| UI/UXデザイン | C | C | R/A | I | - | - |
| 開発・実装 | C | A | C | I | - | - |
| 品質テスト | I | R/A | R | I | - | - |
| 法務レビュー | I | I | - | I | R/A | I |
| 価格設定 | R | I | - | C | C | A |
| マーケティング計画 | C | I | C | R/A | C | I |
| ローンチ判断 | R | C | - | C | C | A |
| プレスリリース | C | I | - | R/A | C | I |

### よくある失敗
1. **Aが複数人いる**: 「全員が責任者」は「誰も責任者でない」と同じ。Aは必ず各タスク1人に絞る
2. **全員がCになっている**: 相談先が多すぎると意思決定が遅くなる。本当に事前相談が必要な人だけをCにする
3. **RACIを作って終わり**: 作成後にチーム全員で合意し、認識のズレがないか確認する。特にAの認識が一致しているかが重要

### 活用のヒント
- まず縦軸（タスク）を洗い出してから、横軸（人/役割）を埋める
- 1つの行にRもAも空欄の場合、そのタスクは宙に浮いている危険信号
- 特定の人にAが集中しすぎていないか確認する。集中はボトルネックの原因
- 空欄は「関与しない」を明示的に意味する。空欄であること自体が重要な情報
- 定期的に見直す。プロジェクトの進行に応じて役割は変わりうる

### 次のステップ
- タスクの依存関係とスケジュールを整理したい → 本スキルの **05. PERT図**
- チームの能力やモチベーションを考慮した配置を考えたい → `/organization`（組織マネジメント）
- 関係者への伝え方を整理したい → `/communication`（ステークホルダーコミュニケーション）
- 戦略的なリソース配分を検討したい → `/strategy`（戦略立案フレームワーク）

## 07. ムリ・ムダ・ムラ（ダラリの法則）
**目的**: 業務の非効率を3つの視点で洗い出す

**いつ使うか**: 業務改善の初期段階で「何が問題か」を網羅的に洗い出したいとき。トヨタ生産方式（TPS）に由来する手法で、製造業だけでなくオフィスワーク・IT業務にも応用可能。

**テンプレート**:
| 視点 | 定義 | 該当する業務 | 改善策 |
|------|------|------------|-------|
| **ムリ**（無理） | 能力以上の負荷がかかっている | | |
| **ムダ**（無駄） | 価値を生まない作業 | | |
| **ムラ**（斑） | 品質や量のばらつき | | |

**使い方**: まず現場の業務を一覧化し、各業務に「ムリ・ムダ・ムラ」のラベルを付ける。

### 記入例（カスタマーサポート部門の改善）

| 視点 | 定義 | 該当する業務 | 影響 | 改善策 |
|------|------|------------|------|-------|
| **ムリ** | 能力以上の負荷 | ・新人が研修3日で電話対応に投入される。マニュアルが500ページあり把握不能 | 新人の離職率40%、誤案内によるクレーム月15件 | ・研修期間を2週間に延長 ・マニュアルを「よくある質問TOP30」に絞った簡易版を作成 ・最初の1ヶ月はベテランとペア対応 |
| **ムリ** | 能力以上の負荷 | ・繁忙期（月末・年度末）に1人あたり1日80件の対応。通常期は40件 | 対応品質の低下、残業月40時間超 | ・繁忙期の臨時スタッフを事前に確保 ・FAQ充実でセルフサービス率を上げる |
| **ムダ** | 価値を生まない作業 | ・同じ顧客情報を3つのシステムに手入力している | 月あたり約60時間の重複作業 | ・システム間のAPI連携を構築し、1回入力で全システムに反映 |
| **ムダ** | 価値を生まない作業 | ・対応完了後に紙の報告書を作成し、上長が確認印を押す | 報告書作成に1件あたり5分、月200件=約17時間 | ・チケットシステムのステータス更新で代替。上長はダッシュボードで確認 |
| **ムラ** | 品質のばらつき | ・担当者によって回答内容が異なる。Aさんは丁寧だがBさんは事務的 | 顧客満足度が担当者依存（NPS: 30-70のばらつき） | ・回答テンプレートを整備 ・月次でロールプレイング研修を実施 ・対応品質のモニタリング指標を導入 |
| **ムラ** | 量のばらつき | ・曜日による問い合わせ量の差が大きい（月曜は金曜の2倍） | 月曜は待ち時間が長く、金曜は余剰人員 | ・曜日別のシフト最適化 ・月曜はチャットボット対応を強化 |

### よくある失敗
1. **ムダだけに注目する**: ムリ（過負荷）は品質低下や離職につながり、ムラ（ばらつき）は顧客体験を損なう。3つの視点をバランスよく見る
2. **改善策が「やめる」一辺倒**: ムリの改善は「負荷を下げる」、ムラの改善は「標準化する」。それぞれ異なるアプローチが必要
3. **現場の声を聞かずにデスクで分析する**: 実際に業務を観察し、担当者にヒアリングすることで初めて本当のムリ・ムダ・ムラが見える

### 活用のヒント
- 業務一覧表を作り、各業務の「所要時間」「頻度」「担当者」を記載した上で分析すると精度が上がる
- ムダの7つの分類（トヨタ式）も参考にする: 作りすぎ、手持ち、運搬、加工、在庫、動作、不良
- 「ムリがムラを生み、ムラがムダを生む」という因果関係を意識する
- 改善効果を「時間」「コスト」「品質」で定量化すると、優先順位がつけやすい

### 次のステップ
- 洗い出した非効率を具体的に排除・改善したい → 本スキルの **08. ECRS**
- 業務の流れを可視化して改善ポイントを特定したい → 本スキルの **04. 業務フロー図**
- 根本原因を深掘りしたい → `/problem`（なぜなぜ分析、特性要因図）
- 改善の優先順位をつけたい → `/idea`（ペイオフマトリクス等の評価フレームワーク）

## 08. ECRS
**目的**: 業務改善を4つの原則で検討する（効果の大きい順）

**いつ使うか**: 業務フロー図やムリ・ムダ・ムラの分析で改善対象が特定された後、具体的な改善策を検討するとき。E→C→R→Sの順に検討することで、最も効果的な改善から着手できる。

**テンプレート**:
| 原則 | 問い | 対象業務 | 改善策 | 削減効果 |
|------|-----|---------|-------|---------|
| **E**liminate（排除） | やめられないか？ | | | |
| **C**ombine（結合） | まとめられないか？ | | | |
| **R**earrange（交換） | 順序や場所を変えられないか？ | | | |
| **S**implify（簡素化） | もっと簡単にできないか？ | | | |

**使い方**: E→C→R→Sの順で検討する。Eliminateが最も効果が大きい（やめるのが最大の改善）。

### 記入例（月次レポート作成業務の改善）

**対象**: 営業部門の月次レポート作成業務（現状: 毎月3営業日、5人で作成）

| 原則 | 問い | 対象業務 | 改善策 | 削減効果 |
|------|-----|---------|-------|---------|
| **E**liminate | やめられないか？ | ・競合動向サマリー（誰も読んでいないことが判明） | 廃止する。必要な人は業界ニュースサービスを直接参照 | 4時間/月 削減 |
| **E**liminate | やめられないか？ | ・個別案件の詳細記述（SFAに同じ情報がある） | SFAのレポート機能で代替。二重作成を廃止 | 8時間/月 削減 |
| **C**ombine | まとめられないか？ | ・営業実績レポートと売上予測レポートが別々に作成されている | 1つのレポートに統合。データソースも一元化 | 6時間/月 削減 |
| **C**ombine | まとめられないか？ | ・地域別と製品別で別々のミーティングで報告 | 月次全体会議1回にまとめ、ダッシュボードで報告 | 会議時間 10時間/月 削減 |
| **R**earrange | 順序を変えられないか？ | ・月末にデータ集計→翌月頭にレポート作成、の直列作業 | データ集計を自動化し、月末時点で速報版を自動生成。翌月は考察の追記のみ | リードタイム 2日→0.5日 |
| **R**earrange | 担当を変えられないか？ | ・マネージャーがデータ集計も分析も担当 | データ集計はアシスタント、分析はマネージャーという分業に変更 | マネージャーの工数 50%削減 |
| **S**implify | 簡単にできないか？ | ・PowerPoint 30ページのレポートを毎月作成 | テンプレートを固定化し、数値とグラフの自動更新。コメント欄のみ手動記入 | 12時間/月 削減 |
| **S**implify | 簡単にできないか？ | ・報告のための社内承認フロー（3段階） | 承認を1段階（部長のみ）に簡素化。内容はダッシュボードでリアルタイム共有 | 承認待ち 3日→1日 |

**改善効果合計**: 月あたり約40時間の工数削減、リードタイム3日→0.5日

### よくある失敗
1. **Simplifyから始めてしまう**: 「効率化」というと自動化・簡素化を考えがちだが、そもそもやめられないか（Eliminate）を最初に考える方が効果が大きい
2. **「やめられない」と即断する**: 「昔からやっているから」「上が見ているから」は本当の理由ではないことが多い。「この業務がなくなったら誰が困るか？」を具体的に問う
3. **定量的な効果を見積もらない**: 「たぶん楽になる」ではなく、削減時間やコストを数字で出すことで、経営層への提案が通りやすくなる

### 活用のヒント
- 改善対象の業務を事前にリストアップし、各業務の所要時間・頻度・担当者を把握してから取り組む
- ECRSの検討結果を一覧表にし、削減効果の大きい順に優先順位をつける
- Eliminateの候補を見つけるには「この業務の成果物を誰が使っているか？」を追跡するのが効果的
- 改善前後の業務フロー図を描くと、変化が視覚的に伝わる
- 改善策の実施後は必ず効果測定を行い、PDCAサイクルに組み込む

### 次のステップ
- 改善策の実行計画を立てたい → 本スキルの **05. PERT図** や **06. RACI**
- 改善効果を継続的にモニタリングしたい → 本スキルの **01. PDCA**
- 改善前後のフローを可視化したい → 本スキルの **04. 業務フロー図**
- 改善提案を経営層にプレゼンしたい → `/communication`（ピラミッドストラクチャー、PREP法）
- 戦略的な業務設計を行いたい → `/strategy`（ビジネスモデル設計）

## 対話の進め方

### ステップ1: 課題のヒアリング
ユーザーに以下を確認する:
- **何を改善したいか**: 特定の業務プロセス？チーム全体の働き方？プロジェクトの進め方？
- **現状の問題意識**: 何が「うまくいっていない」と感じているか？具体的なエピソードがあるか？
- **改善の目的**: コスト削減？品質向上？スピードアップ？社員の負担軽減？
- **対象範囲**: 個人の業務？チーム？部門横断？全社？
- **制約条件**: 予算、人員、期間、システム上の制約はあるか？

### ステップ2: フレームワークの提案
課題に応じて最適なフレームワークを提案する。以下の選定ガイドを使う:

| ユーザーの課題 | 推奨フレームワーク | 理由 |
|-------------|----------------|------|
| 「振り返りをしたい」「前回のプロジェクトの反省をしたい」 | **KPT** または **YWT** | KPTはチーム向け、YWTは個人向け・学び重視 |
| 「業務の無駄を減らしたい」「効率化したい」 | **ムリ・ムダ・ムラ** → **ECRS** | まず非効率を洗い出し、次に具体的な改善策を検討 |
| 「業務の流れを整理したい」「ボトルネックを見つけたい」 | **業務フロー図** | 可視化が第一歩 |
| 「プロジェクトのスケジュールを組みたい」 | **PERT図** | タスクの依存関係と所要時間から計画を立てる |
| 「誰が何をやるか明確にしたい」 | **RACI** | 役割分担の可視化 |
| 「継続的に改善していきたい」 | **PDCA** | 改善サイクルの構築 |
| 「複数の問題がある。何から手をつけるべきか」 | **ムリ・ムダ・ムラ** で全体把握 → **ECRS** で優先順位付け | 網羅的な洗い出しから始める |

複数のフレームワークを組み合わせることが多い。典型的な組み合わせ:
- **業務改善の王道**: 業務フロー図（現状把握）→ ムリ・ムダ・ムラ（問題特定）→ ECRS（改善策立案）→ PDCA（実行・検証）
- **プロジェクト立ち上げ**: RACI（役割定義）→ PERT図（スケジュール）→ PDCA（進捗管理）
- **定期振り返り**: KPT（チーム振り返り）→ PDCA（改善実行）→ KPT（次の振り返り）

### ステップ3: 対話的にテンプレートを埋める
- 一度にすべてを埋めようとせず、セクションごとに進める
- ユーザーの回答が曖昧な場合は、具体例を示して深掘りする
- 「他にありますか？」と漏れを確認する
- 記入例を参考に示しながら、ユーザー自身の言葉で埋めてもらう

### ステップ4: 分析とインサイトの提供
テンプレートが埋まったら、以下の観点で分析を加える:
- パターンや傾向の指摘（「3つの問題に共通する根本原因がありそうです」）
- 優先順位の提案（「効果とコストの観点から、この順序で取り組むのがおすすめです」）
- 見落としがちな観点の補足（「ステークホルダーへの影響も考慮しましょう」）

### ステップ5: 完成したワークシートの出力
- Markdown形式で整形して出力する
- 必要に応じて、次のアクションアイテムのリストを添える
- 他のフレームワーク（他のスキル）への接続を提案する
