# 組織・チームマネジメントフレームワーク

ユーザーの $ARGUMENTS に基づき、以下のフレームワークから適切なものを適用してください。

---

## 01. ミッション・ビジョン・バリュー（MVV）
**目的**: 組織の存在意義・目指す姿・行動指針を言語化し、共通の拠り所を作る

**テンプレート**:
| 要素 | 定義 | 内容 |
|------|------|------|
| **Mission** | 何のために存在するか（存在意義） | |
| **Vision** | どこを目指すか（将来像） | |
| **Values** | 何を大切にするか（行動指針） | ・ |

**使い方**: Mission（不変）→ Vision（5-10年）→ Values（日常の判断基準）の順で策定する。Missionは「なぜこの組織が世の中に必要なのか」という根源的な問い。Visionは「Mission達成に向けて、中長期的にどんな姿になっていたいか」。Valuesは「その過程で、日々の意思決定や行動をどう選ぶか」を具体的に定める。

### 記入例

| 要素 | 定義 | 内容 |
|------|------|------|
| **Mission** | 何のために存在するか（存在意義） | テクノロジーの力で、すべての人が金融サービスに平等にアクセスできる社会を実現する |
| **Vision** | どこを目指すか（将来像） | 2030年までにアジア太平洋地域で最も信頼されるフィンテック企業となり、1億人の金融包摂を達成する |
| **Values** | 何を大切にするか（行動指針） | ・ユーザーファースト：すべての意思決定の起点は利用者の課題解決である ・透明性：情報はオープンにし、誠実に説明責任を果たす ・挑戦と学習：失敗を恐れず試し、そこから素早く学ぶ ・多様性の尊重：異なる視点がイノベーションの源泉である |

### よくある失敗
1. **MissionとVisionの混同**: Missionを「売上1000億円」のような数値目標にしてしまう。Missionは数値ではなく、組織の存在意義（Why）を表すもの。数値目標はVisionや経営計画に含める
2. **Valuesが抽象的すぎて行動に落ちない**: 「イノベーション」「チームワーク」のような一般的な言葉を並べるだけでは、日々の判断基準にならない。「具体的にどう行動すればこのValueを体現できるか」を明文化する
3. **経営層だけで策定して現場に浸透しない**: MVVは共感と納得が不可欠。策定プロセスに現場メンバーを巻き込むか、策定後に丁寧な対話を通じて「自分ごと化」する仕組みが必要

### 活用のヒント
- Missionを検証するテスト：「もしこの組織がなくなったら、社会は何を失うか？」を問いかける
- Valuesは3〜5つに絞る。7つ以上あると覚えられず形骸化する
- Valuesに優先順位をつけておくと、価値観が衝突した場面で意思決定しやすくなる（例：「ユーザーファースト」と「スピード」が衝突したときは前者を優先）
- 半年に1回程度、MVVの浸透度を振り返る場を設ける。朝会や1on1で「最近MVVを意識した場面」を共有するのも有効

### 次のステップ
- MVVを策定した後は、**ステークホルダー分析**（06）で関係者への浸透方針を設計する
- Valuesを具体的な行動指針に落とし込む際は、**strategy**スキルの戦略フレームワークと連動させると一貫性が保てる
- 組織文化の課題が見えてきたら、**動機付け・衛生理論**（07）で社員のモチベーション構造を分析する

## 02. Will／Can／Must
**目的**: 個人のキャリアや役割を「やりたい」「できる」「求められている」の3つで整理する

**テンプレート**:
```
      Will（やりたいこと）
         ／    ＼
        ／  ★  ＼
       ／ 理想  ＼
Can ──────────── Must
（できること）  （求められていること）
```

| 領域 | 内容 |
|------|-----|
| **Will**（やりたいこと） | |
| **Can**（できること） | |
| **Must**（やるべきこと） | |
| **Will ∩ Can ∩ Must** | ← ここが最も充実するゾーン |

**使い方**: まず各領域を洗い出し、次に重なりの部分を特定する。3つすべてが重なる領域が「最も充実感を持って成果を出せるゾーン」。重なりが小さい場合は、Canを広げる（学習）、Willを明確にする（自己理解）、Mustを調整する（上司との対話）のいずれかでゾーンを拡大する。

### 記入例

| 領域 | 内容 |
|------|-----|
| **Will**（やりたいこと） | ・新規事業の立ち上げに携わりたい ・データ分析を使った意思決定に関わりたい ・チームをリードする経験を積みたい ・海外市場に関わる仕事がしたい |
| **Can**（できること） | ・Pythonによるデータ分析・可視化 ・既存プロダクトのマーケティング運用 ・英語でのビジネスコミュニケーション（TOEIC 850） ・プロジェクト管理（3年経験） |
| **Must**（やるべきこと） | ・既存事業のKPI改善（今期の部門目標） ・後輩2名の育成・OJT ・新CRMツール導入プロジェクトのリード ・月次報告書の作成と経営会議での報告 |
| **Will ∩ Can ∩ Must** | データ分析スキルを活かしてCRM導入プロジェクトをリードしつつ、そのプロセスで後輩を育成する。CRMのデータ分析基盤を新規事業検討の土台としても活用する |

### よくある失敗
1. **Willが「なんとなく」のまま終わる**: 「面白い仕事がしたい」のような漠然としたWillでは交差点が見つからない。「なぜそれをやりたいのか」を5回掘り下げ、具体的な行動レベルまで言語化する
2. **Canを過小評価する**: 自分では当たり前だと思っているスキルや経験を見落としがち。周囲にフィードバックをもらうか、ジョハリの窓（04）と組み合わせると盲点が見つかる
3. **Mustを「与えられたもの」として固定化する**: Mustは交渉や提案で変えられる場合も多い。上司との1on1でWillとCanを共有し、Mustの調整余地を探る姿勢が重要

### 活用のヒント
- 1on1ミーティングの事前準備として本人に記入してもらい、対話の起点にすると効果的
- 四半期ごとに更新すると、キャリアの変化を追跡できる
- CanからWillへの矢印（やってみたら面白かった）、MustからCanへの矢印（やらざるを得ず身についた）も意識すると、キャリアの視野が広がる
- チーム全体で共有すると、メンバー間の役割分担やジョブアサインの最適化に活用できる

### 次のステップ
- Canの深掘りには**ジョハリの窓**（04）を併用し、他者から見た強みを発見する
- 具体的な行動計画に落とし込むには**GROWモデル**（09）でコーチング的に対話する
- チームメンバー全員分を並べて分析する場合は**Will/Skillマトリクス**（08）でマネジメント方針を決める
- キャリアプランの策定には**strategy**スキルの目標設定フレームワークと組み合わせる

## 03. Need／Wantマトリクス
**目的**: 組織やメンバーの要求を「必要性」と「欲求」で分類し、優先順位を明確にする

**テンプレート**:
|  | Want（欲しい） | Not Want（欲しくない） |
|---|-------------|-------------------|
| **Need（必要）** | 最優先で取り組む | 説得・動機付けが必要 |
| **Not Need（不要）** | 期待値の調整が必要 | 対応不要 |

**使い方**: Needは客観的・合理的な必要性（事業や組織として欠かせないもの）、Wantは主観的な欲求（本人やチームが望んでいるもの）。この2軸を分けることで、「やりたいけど不要なもの」への過剰投資や、「必要だけどやりたくないもの」の放置を防ぐ。

### 記入例（エンジニアチームのツール導入検討）

|  | Want（欲しい） | Not Want（欲しくない） |
|---|-------------|-------------------|
| **Need（必要）** | CI/CDパイプラインの刷新（チームも望んでおり、リリース品質向上に不可欠） | セキュリティ監査ツールの導入（面倒だが、コンプライアンス要件で必須） |
| **Not Need（不要）** | 最新フレームワークへの移行（エンジニアは興味があるが、現行で問題なく動作中） | レガシーな社内ツールの機能追加（誰も望んでおらず、廃止予定） |

### よくある失敗
1. **NeedとWantを混同する**: 「メンバーが強く望んでいる＝必要」と判断してしまう。Needの判定基準は事業インパクト・リスク・制約条件であり、感情とは切り離して評価する
2. **Need × Not Wantの象限を放置する**: 「必要だけど誰もやりたくないこと」は最も放置されやすく、かつ最も深刻な問題を引き起こす。この象限には意図的にリソースとインセンティブを割り当てる
3. **4象限に分けただけで満足する**: 分類はあくまで出発点。各象限に対する具体的なアクション（誰が・いつまでに・何をするか）まで落とし込む必要がある

### 活用のヒント
- チームの要望を集約する際に使うと、限られたリソースの配分を客観的に説明できる
- Need × Not Wantの項目には「なぜ必要か」のストーリーを丁寧に伝える。動機付け・衛生理論（07）の考え方が役立つ
- 四半期の施策レビューで使うと、「やっていて楽しいが効果が薄い施策」の見直しに有効
- 複数のステークホルダーがいる場合、各者のNeed/Wantを並べて比較すると、合意形成の突破口が見える

### 次のステップ
- Need × Not Wantの項目でメンバーの動機づけが課題なら**動機付け・衛生理論**（07）を使う
- 複数の利害関係者間でNeed/Wantが衝突する場合は**ステークホルダー分析**（06）で対応方針を設計する
- 優先順位の付け方に迷ったら**problem**スキルの問題解決フレームワーク（ロジックツリーや優先順位マトリクス）を活用する
- 施策の実行計画には**execution**スキルのプロジェクト管理フレームワークを使う

## 04. ジョハリの窓
**目的**: 自己認識と他者認識のギャップを可視化し、相互理解を深める

**テンプレート**:
|  | 自分が知っている | 自分が知らない |
|---|---------------|-------------|
| **他者が知っている** | 開放の窓（Open） | 盲点の窓（Blind） |
| **他者が知らない** | 秘密の窓（Hidden） | 未知の窓（Unknown） |

**使い方**: 「開放の窓」を広げることが信頼関係構築の鍵。フィードバック（盲点の窓→開放）と自己開示（秘密の窓→開放）で広げる。

### 記入例（営業マネージャーAさんの場合）

|  | 自分が知っている | 自分が知らない |
|---|---------------|-------------|
| **他者が知っている** | **開放の窓**: 提案力が高い、数字への執着が強い、プレゼンが上手い、朝型で早く出社する | **盲点の窓**: 会議で他者の意見を遮りがち、後輩が質問しづらい雰囲気を出している、資料の細部にミスが多い |
| **他者が知らない** | **秘密の窓**: 実はマネジメントに自信がない、将来は独立したいと思っている、数字が未達の月は眠れなくなる | **未知の窓**: 文章を書く才能がある（まだ試したことがない）、メンタリングの適性が高い（まだ機会がない） |

### よくある失敗
1. **フィードバックを受け取る準備ができていない状態で実施する**: 心理的安全性が低いチームでいきなり「盲点を指摘し合おう」とすると、防衛反応が出て逆効果になる。まず「秘密の窓」の自己開示から始め、信頼関係を築く
2. **ネガティブな情報だけに偏る**: 盲点の窓＝ダメ出し、と捉えがち。「あなたの強みでまだ自覚していないもの」（ポジティブな盲点）を中心にフィードバックすると、受け入れやすくなる
3. **一度きりで終わらせる**: ジョハリの窓は継続的に更新されるもの。定期的（四半期に1回など）に実施して変化を追跡することで、成長の実感と信頼関係の深化が得られる

### 活用のヒント
- チーム全体でワークショップ形式で行う場合は、まず各自が自分の特徴を10個書き出し、次に他者の特徴を10個書き出し、それらを突き合わせると4象限が埋まる
- 1on1で使う場合は「最近あなたについて感じたこと」をマネージャーからフィードバックし、「実は考えていること」を本人に自己開示してもらう
- 「未知の窓」を探索するには、普段と異なる仕事や役割にチャレンジする機会を意図的に作る
- 盲点の窓のフィードバックは「SBI（Situation-Behavior-Impact）」形式で伝えると具体的で受け取りやすい

### 次のステップ
- 盲点の窓で発見した強みや課題を踏まえて、**Will/Can/Must**（02）を更新する
- フィードバックの伝え方を磨くには**communication**スキルのフレームワークを活用する
- チーム全体の相互理解が深まったら、**PM理論**（05）でリーダーシップスタイルを診断する
- 未知の窓を開拓するための行動計画は**GROWモデル**（09）で設計する

## 05. PM理論
**目的**: リーダーシップを「目標達成機能（P: Performance）」と「集団維持機能（M: Maintenance）」の2軸で診断する

**テンプレート**:
|  | M機能：高 | M機能：低 |
|---|---------|---------|
| **P機能：高** | **PM型**（理想） | **Pm型**（成果重視） |
| **P機能：低** | **pM型**（人間関係重視） | **pm型**（要改善） |

**自己診断**:
- P機能（目標設定、計画、指示、評価）: 高/中/低
- M機能（傾聴、配慮、葛藤解決、チーム形成）: 高/中/低
- 現在の類型: 

**詳細チェックリスト**:

| P機能の要素 | 自己評価（1-5） | 具体的な行動例 |
|------------|---------------|-------------|
| 目標の明確化 | | チームの目標を数値で定義し、全員に共有している |
| 計画と段取り | | タスクの優先順位と期限を設定し、進捗を管理している |
| 的確な指示 | | メンバーに求める成果物と品質水準を明確に伝えている |
| 評価とフィードバック | | 成果を定量的に評価し、改善点を具体的に伝えている |
| 問題解決の推進 | | 障害が発生した際に迅速に判断し、対処策を実行している |

| M機能の要素 | 自己評価（1-5） | 具体的な行動例 |
|------------|---------------|-------------|
| 傾聴と共感 | | メンバーの話を最後まで聞き、感情を受け止めている |
| 個別配慮 | | メンバーそれぞれの事情や状況を把握し、対応を変えている |
| 葛藤の解決 | | メンバー間の対立を早期に察知し、仲裁・調整している |
| チームの一体感醸成 | | チームの成功を全員で祝い、帰属意識を高めている |
| 心理的安全性の確保 | | 失敗を責めず、挑戦や発言を奨励する雰囲気を作っている |

### 記入例（プロダクト開発チームのマネージャーBさん）

- P機能: 高（目標設定が明確、スプリントの計画精度が高い、KPIレビューを毎週実施）
- M機能: 低（1on1が形骸化、メンバーの不満に気づくのが遅い、チーム内の対立を放置しがち）
- 現在の類型: **Pm型**（成果重視型）
- 課題: メンバーの離職が続いている。成果は出ているが、チームの雰囲気が悪化
- 改善方針: M機能を強化する。具体的には、1on1の質を上げる（傾聴を意識）、チームビルディングの機会を月1回設ける、メンバーの感情面の変化を週次で確認する

### よくある失敗
1. **PM型を万能と考え、常にPM型を目指す**: 状況によってはPm型のリーダーシップが必要な場面もある（危機対応、短期的な立て直し等）。重要なのは「今のチームに何が足りないか」を見極めること
2. **P機能とM機能をトレードオフと捉える**: 「厳しくすると嫌われる」「優しくすると成果が出ない」という二項対立は誤解。P機能とM機能は独立した軸であり、両方を同時に高めることが可能
3. **自己評価だけで診断する**: リーダー自身の認識と、メンバーから見た認識にはギャップがある。360度フィードバックやジョハリの窓（04）と組み合わせて診断する

### 活用のヒント
- リーダーの成長段階として、まずP機能を身につけ（仕事を回す力）、次にM機能を高める（人を活かす力）順番が実務的
- Pm型のリーダーがM機能を高めるには、まず「傾聴」を1つだけ徹底する。1on1で自分が話す時間を全体の30%以下にするルールを設ける
- pM型のリーダーがP機能を高めるには、「曖昧な指示をしない」を1つだけ徹底する。依頼時に「何を・いつまでに・どの品質で」を必ず明示する
- チーム全体のリーダーシップ力を高めるには、PM理論を共有言語にして、メンバー同士でP/M機能のフィードバックを交換する

### 次のステップ
- M機能の強化が課題なら**GROWモデル**（09）でコーチングスキルを磨く
- メンバー個別のマネジメント方法は**Will/Skillマトリクス**（08）で設計する
- リーダーとしての自己理解を深めるには**ジョハリの窓**（04）で360度フィードバックを受ける
- チーム全体の課題を構造化するには**problem**スキルの問題解決フレームワークを活用する

## 06. ステークホルダー分析
**目的**: プロジェクトに関わる利害関係者を特定し、影響力と関心度に応じた対応方針を決める

**テンプレート**:
| ステークホルダー | 関心事 | 影響力 | 関心度 | 対応方針 |
|--------------|-------|-------|-------|---------|
| | | 高/低 | 高/低 | |

**対応マトリクス**:
|  | 関心度：高 | 関心度：低 |
|---|----------|----------|
| **影響力：高** | 密に管理（Key Player） | 満足を維持 |
| **影響力：低** | 情報提供を継続 | モニタリング |

**使い方**: (1) ブレインストーミングでステークホルダーを網羅的に洗い出す (2) 各者の関心事を整理する (3) 影響力と関心度で4象限にマッピングする (4) 象限ごとに対応方針とコミュニケーション頻度を決める。

### 記入例（社内DX推進プロジェクト）

| ステークホルダー | 関心事 | 影響力 | 関心度 | 対応方針 |
|--------------|-------|-------|-------|---------|
| CEO | ROI、競争優位性 | 高 | 高 | 月次で進捗報告、経営会議でデモ。意思決定の承認を得る |
| CFO | 投資対効果、コスト管理 | 高 | 中 | 四半期ごとに費用対効果レポートを提出。予算超過リスクを早期共有 |
| 情報システム部長 | セキュリティ、既存システムとの整合 | 高 | 高 | 週次で技術的な相談。設計レビューに必ず参加してもらう |
| 営業部門（ユーザー部門） | 業務負荷の増減、使い勝手 | 低 | 高 | 月次で説明会を開催。パイロットユーザーを選出し、早期にフィードバックを収集 |
| 外部ベンダー | 契約範囲、スケジュール | 中 | 高 | 週次定例で進捗確認。スコープ変更は文書で合意 |
| 人事部 | 人員配置、教育研修 | 低 | 低 | 必要に応じて情報共有。大きな組織変更がある場合のみ相談 |

### よくある失敗
1. **可視化されにくいステークホルダーを見落とす**: 直接的な利害関係者だけでなく、間接的に影響を受ける人（隣接部門、顧客、組合、外部規制当局など）も洗い出す。「この変化で困る人は誰か」を問いかけると漏れが減る
2. **影響力と関心度を静的に捉える**: プロジェクトのフェーズが変わると、各ステークホルダーの影響力や関心度も変動する。フェーズごと（企画・設計・実行・定着）に見直す
3. **Key Playerへの対応に偏り、他の象限を放置する**: 「影響力は低いが関心度が高い」グループ（現場ユーザーなど）を軽視すると、導入後の抵抗や形骸化を招く

### 活用のヒント
- 最初の洗い出しは「組織図を見ながら」やると漏れが少ない。組織の外側（顧客・取引先・規制当局）も忘れずに
- 各ステークホルダーの「賛成/中立/反対」のスタンスも記録しておくと、味方づくりの戦略が立てやすい
- 反対派のステークホルダーには「何が変われば賛成に転じるか」を個別にヒアリングする
- 対応方針にはコミュニケーションの頻度・手段・担当者まで決めておくと実行が止まらない

### 次のステップ
- Key Playerとの交渉や説得には**communication**スキルのフレームワーク（説得・交渉術）を活用する
- ステークホルダー間の利害対立がある場合は**problem**スキルの問題解決フレームワークで構造化する
- プロジェクト全体の実行管理には**execution**スキルのフレームワークを使う
- 反対派の動機を理解するには**動機付け・衛生理論**（07）の視点が役立つ

## 07. 動機付け・衛生理論（ハーズバーグ）
**目的**: モチベーション要因を「動機付け要因」と「衛生要因」に分けて、打ち手を設計する

**テンプレート**:
| 要因タイプ | 要素 | 現状（満/不満） | 改善策 |
|----------|------|-------------|-------|
| **動機付け要因** | 達成感 | | |
| （満たすと満足↑） | 承認 | | |
| | 仕事そのもの | | |
| | 責任 | | |
| | 成長・昇進 | | |
| **衛生要因** | 給与 | | |
| （不足すると不満↑） | 人間関係 | | |
| | 労働条件 | | |
| | 会社の方針 | | |
| | 管理方法 | | |

**使い方**: 衛生要因の不満を解消してから、動機付け要因を強化する。衛生要因を満たしてもモチベーションは上がらない（不満が減るだけ）。動機付け要因こそがモチベーションを引き上げるドライバーである。

### 記入例（離職率が高いWebエンジニアチームの分析）

| 要因タイプ | 要素 | 現状（満/不満） | 改善策 |
|----------|------|-------------|-------|
| **動機付け要因** | 達成感 | 不満（リリースが延期続きで成功体験が少ない） | スプリントゴールを小さく設定し、2週間ごとに達成感を得られるようにする |
| （満たすと満足↑） | 承認 | 不満（良い仕事をしても特にフィードバックがない） | 週次のチームレビューで貢献を可視化。Slackで称賛チャンネルを運用 |
| | 仕事そのもの | 満（技術的に挑戦的なプロダクト） | 現状維持。テックブログ執筆を奨励してアウトプットの機会を増やす |
| | 責任 | 不満（マイクロマネジメントが多い） | チームにオーナーシップを移譲。意思決定権限を明文化する |
| | 成長・昇進 | 不満（キャリアパスが不明確） | エンジニアリングラダーを策定し、四半期ごとにキャリア面談を実施 |
| **衛生要因** | 給与 | 不満（市場相場より15%低い） | 来期の報酬改定で市場相場に合わせる。成果連動ボーナスを導入 |
| （不足すると不満↑） | 人間関係 | 満（チーム内の雰囲気は良好） | 現状維持。チームビルディング予算を確保 |
| | 労働条件 | 不満（リモート勤務が週1日に制限） | 週3日リモート勤務を許可。コアタイムを短縮しフレックスを拡充 |
| | 会社の方針 | 満（ミッションに共感している） | MVVの浸透活動を継続 |
| | 管理方法 | 不満（評価基準が曖昧） | 評価基準を透明化。自己評価→上司評価→すり合わせのプロセスを導入 |

**優先順位**: まず衛生要因の不満（給与・労働条件・管理方法）を解消し、次に動機付け要因（達成感・承認・責任・成長）を強化する

### よくある失敗
1. **給与を上げればモチベーションが上がると考える**: 給与は衛生要因なので、上げても「不満が減る」だけ。一定水準を超えたら、動機付け要因にリソースを振り向ける方が効果的
2. **動機付け要因と衛生要因を混同する**: 「福利厚生を充実させたのに離職が止まらない」場合、衛生要因ばかり改善して動機付け要因が放置されている可能性が高い
3. **全員に同じ打ち手を適用する**: 人によって動機付け要因の優先度は異なる。達成感を重視する人と承認を重視する人では、有効なアプローチが違う。1on1で個別にヒアリングする

### 活用のヒント
- エンゲージメントサーベイの結果を10項目に分解して本テンプレートに当てはめると、打ち手の設計がしやすい
- 「不満は声に出やすいが、満足は声に出にくい」ことを意識する。不満の声だけを拾って衛生要因ばかり改善すると、動機付け要因が見落とされる
- 採用競争力の観点では、衛生要因はテーブルステークス（最低限必要な条件）、動機付け要因が差別化要因と捉える
- 改善策は「コスト」と「インパクト」で優先順位をつける。承認（褒める・感謝する）はコストゼロで即効性が高い

### 次のステップ
- 個別メンバーの動機を深掘りするには**GROWモデル**（09）でコーチング対話を行う
- メンバーの意欲と能力のバランスは**Will/Skillマトリクス**（08）で可視化する
- 組織全体の方針・文化が課題なら**MVV**（01）の再策定を検討する
- 具体的な改善施策の立案には**improvement**スキルのフレームワークを活用する

## 08. Will／Skillマトリクス
**目的**: メンバーの意欲と能力に応じたマネジメントスタイルを選択する

**テンプレート**:
|  | Skill：高 | Skill：低 |
|---|---------|---------|
| **Will：高** | 委任（Delegate） | 指導（Guide） |
| **Will：低** | 刺激（Excite） | 指示（Direct） |

**各象限の詳細**:

| 象限 | 特徴 | マネジメント方針 | コミュニケーション頻度 |
|------|------|---------------|-------------------|
| **委任（Delegate）** | 高意欲・高能力。自律的に成果を出せる | 目標と権限を与えて任せる。細かい進捗管理は不要。成果で評価する | 週1回の1on1。必要時に相談に乗る |
| **指導（Guide）** | 高意欲・低能力。やる気はあるがスキル不足 | 丁寧にティーチングする。失敗を許容しつつ、段階的に難易度を上げる | 毎日〜週2-3回のチェックイン。ペアワークやメンター制度 |
| **刺激（Excite）** | 低意欲・高能力。能力はあるがモチベーション低下 | 本人の関心を引き出す。裁量や挑戦的なテーマを与える。「なぜやる気が出ないか」を深掘りする | 週1回の1on1で丁寧に傾聴。キャリアの方向性を対話 |
| **指示（Direct）** | 低意欲・低能力。最も手厚いサポートが必要 | 明確な指示と短いサイクルの確認。小さな成功体験を積ませる | 毎日のチェックイン。タスクを細分化して達成感を演出 |

**メンバー配置**:
| メンバー | Will | Skill | 象限 | マネジメント方針 |
|---------|------|-------|------|---------------|
| | 高/低 | 高/低 | | |

### 記入例（マーケティングチーム5名の診断）

| メンバー | Will | Skill | 象限 | マネジメント方針 |
|---------|------|-------|------|---------------|
| 田中さん（シニア） | 高 | 高 | 委任 | 新規チャネル開拓を一任。月次で成果報告を受ける。次期リーダー候補として権限を拡大 |
| 佐藤さん（中堅） | 低 | 高 | 刺激 | 最近マンネリ化。新規プロジェクトのリードを打診。キャリアの方向性を1on1で対話 |
| 鈴木さん（若手） | 高 | 低 | 指導 | やる気は十分だがSNS運用スキルが不足。田中さんのメンターの下でOJT。月2回の勉強会 |
| 高橋さん（若手） | 高 | 低 | 指導 | データ分析に興味があるが経験不足。外部研修を受講させつつ、レポート作成から段階的に |
| 渡辺さん（中途） | 低 | 低 | 指示 | 前職とのギャップに苦戦中。まず業務マニュアルの整備から。日次で15分のチェックイン |

### よくある失敗
1. **全メンバーに同じマネジメントスタイルを適用する**: 「自分はこのスタイル」と固定してしまうリーダーが多い。委任型リーダーが指示象限のメンバーを放置したり、指示型リーダーが委任象限のメンバーをマイクロマネジメントしたりする
2. **WillとSkillの判断を主観だけで行う**: マネージャーの印象だけでなく、本人との対話（Will）と実績データ（Skill）で判断する。特にWillは表面的な態度と内面が異なることが多い
3. **象限を固定的に捉える**: 人は成長し変化する。「指導」象限のメンバーがスキルアップして「委任」に移る過程を計画的にデザインする。逆に「委任」象限のメンバーが「刺激」象限に移る（燃え尽き）ケースも早期に検知する

### 活用のヒント
- 四半期ごとにマトリクスを更新し、メンバーの成長（象限の移動）を追跡する
- 「刺激」象限のメンバーには、まず「なぜWillが低いのか」を理解することが最優先。原因は仕事内容、人間関係、プライベート、キャリア不安など多様
- 「指導」象限のメンバーは最も投資効率が高い。適切なサポートで最も早く「委任」象限に移行する
- チーム全体で「委任」象限のメンバーが少ない場合、リーダーに業務が集中しやすい。中期的に「委任」メンバーを育成する計画が不可欠

### 次のステップ
- 「刺激」象限のメンバーの動機を深掘りするには**動機付け・衛生理論**（07）を活用する
- 各メンバーとの1on1対話には**GROWモデル**（09）のフレームワークを使う
- メンバーの自己認識と他者認識のギャップ把握には**ジョハリの窓**（04）が有効
- メンバーのキャリア開発には**Will/Can/Must**（02）を組み合わせる
- スキルアップの具体的な計画には**execution**スキルのアクションプラン策定を使う

## 09. GROWモデル
**目的**: コーチングの基本フレーム。対話を通じてメンバーの自発的な行動を引き出す

**テンプレート**:
| ステップ | 問い | メンバーの回答 |
|---------|------|-------------|
| **G**oal（目標） | 何を達成したいですか？ | |
| **R**eality（現状） | 今はどんな状況ですか？ | |
| **O**ptions（選択肢） | どんな方法がありますか？ | |
| **W**ill（意志） | 具体的に何をしますか？いつまでに？ | |

**使い方**: コーチは答えを与えず、問いかけでメンバー自身に考えさせる。「他には？」「具体的には？」で深掘りする。

**各ステップの詳細な問いかけ例**:

| ステップ | 目的 | 効果的な問いかけ例 |
|---------|------|-----------------|
| **Goal** | ありたい姿を明確にする | ・「理想的な状態を具体的に描くとどんなイメージですか？」 ・「それが達成できたとき、何が変わっていますか？」 ・「その目標は、あなたにとってなぜ重要ですか？」 ・「3ヶ月後にどうなっていたら成功と言えますか？」 |
| **Reality** | 現状を客観的に把握する | ・「今は10点満点で何点くらいですか？」 ・「これまでに試したことは何ですか？その結果はどうでしたか？」 ・「何が一番の障害になっていますか？」 ・「この状況を周りの人はどう見ていると思いますか？」 |
| **Options** | 可能性を広げる | ・「他にはどんな方法が考えられますか？」（3つ以上引き出す） ・「もし制約がなかったら、何をしますか？」 ・「うまくやっている人は、どうしていると思いますか？」 ・「それぞれの選択肢のメリット・デメリットは？」 |
| **Will** | 行動にコミットする | ・「その中で、最も効果的だと思うのはどれですか？」 ・「具体的に、最初の一歩は何ですか？」 ・「いつまでにやりますか？」 ・「実行を妨げそうなことは何ですか？どう対処しますか？」 ・「私にサポートしてほしいことはありますか？」 |

### 記入例（若手エンジニアのキャリア相談）

| ステップ | 問い | メンバーの回答 |
|---------|------|-------------|
| **Goal** | 半年後にどうなっていたいですか？ | バックエンドだけでなく、フロントエンドも含めてフルスタックで1機能を任せてもらえるレベルになりたい |
| **Reality** | 今のスキル状況は？10点満点で？ | バックエンドは7点。フロントエンドは3点。Reactの基礎は独学で勉強したが、実務経験がない。社内にフロントエンド専任がいないので相談相手がいない |
| **Options** | どんな方法が考えられますか？ | (1) 社内の小さなフロントエンドタスクを引き受ける (2) 外部の実践的なオンライン講座を受講する (3) 個人プロジェクトでポートフォリオを作る (4) 社外のフロントエンドエンジニアとのメンタリングを探す |
| **Will** | 最初に何をしますか？ | 来週中に、今のプロダクトのフロントエンド改善タスクを1つPMに提案する。並行して、UdemyのReact実践コースを今月中に完了する。進捗は隔週の1on1で報告する |

### よくある失敗
1. **Goalが曖昧なまま先に進む**: 「成長したい」「もっとうまくやりたい」のような漠然としたGoalでは、Reality以降が散漫になる。「いつまでに」「何ができる状態を」「どう測定するか」を具体化するまでGoalステップに留まる
2. **Optionsで選択肢を十分に広げない**: 1-2個の選択肢で「これでいこう」と決めてしまうと、最善の方法を見逃す可能性がある。最低3つ、できれば5つ以上の選択肢を引き出す。「他には？」を粘り強く繰り返す
3. **コーチがアドバイスしてしまう**: 「こうすればいいんじゃない？」と答えを与えると、メンバーの自律性が育たない。どうしてもアドバイスしたい場合は「1つ提案してもいいですか？」と許可を得てから伝える

### 活用のヒント
- 1on1ミーティングの後半15分でGROWモデルを回すのが実践的。最初は「今日のGROW」としてテーマを1つ決めて対話する
- Goalは「セッションのゴール」と「最終的なゴール」を分けると進めやすい。例：最終ゴール「フルスタックエンジニアになる」→セッションゴール「今月取り組むことを1つ決める」
- メンバーが「分からない」と言ったときは、沈黙を恐れない。10秒待つだけで自分で考え始めることが多い
- GROWの順番は厳密に守る必要はない。RealityからGoalに戻ったり、OptionsからRealityに戻ることもある。自然な対話の流れを優先する
- セッション終了時に「今日の対話で一番の気づきは？」と聞くと、学びが定着しやすい

### 次のステップ
- GROWモデルで出てきた行動計画を実行するには**execution**スキルのタスク管理フレームワークを使う
- Goalの背景にあるキャリアの方向性を整理するには**Will/Can/Must**（02）を活用する
- メンバーのWillやSkillの状態に応じてGROWの使い方を変えるには**Will/Skillマトリクス**（08）を参照する
- 組織全体の課題がGROWの中で見えてきた場合は**動機付け・衛生理論**（07）や**MVV**（01）に立ち返る
- 問題の構造化が必要な場合は**problem**スキルのフレームワークでロジカルに分解する

## 対話の進め方

### フェーズ1: 状況のヒアリング

AskUserQuestionで以下を確認する:

1. **組織の基本情報**
   - チーム/組織の規模（何名程度か）
   - 業種・業態
   - ユーザーの役割（経営者、マネージャー、メンバー等）

2. **課題の特定**
   - 「今、組織やチームで一番困っていることは何ですか？」
   - 「それはいつ頃から起きていますか？」
   - 「すでに試したことはありますか？その結果は？」

3. **ゴールの明確化**
   - 「この対話を通じて、どんな状態になりたいですか？」
   - 「具体的なアウトプットとして何が欲しいですか？（分析結果、アクションプラン、チェックリスト等）」

### フェーズ2: フレームワークの選定と提案

ユーザーの課題に基づき、最適なフレームワークを1〜3つ提案する。選定基準:

| 課題の種類 | 推奨フレームワーク |
|-----------|-----------------|
| 組織の方向性が定まらない | MVV（01） |
| メンバーのキャリア・役割が不明確 | Will/Can/Must（02） |
| 施策やリソースの優先順位がつかない | Need/Wantマトリクス（03） |
| チーム内のコミュニケーション不全 | ジョハリの窓（04） |
| リーダーシップの課題 | PM理論（05） |
| プロジェクトの関係者管理 | ステークホルダー分析（06） |
| メンバーのモチベーション低下・離職 | 動機付け・衛生理論（07） |
| メンバーごとのマネジメント方法 | Will/Skillマトリクス（08） |
| 1on1やコーチングの質向上 | GROWモデル（09） |

複数の課題が絡み合っている場合は、フレームワークの組み合わせを提案する。例:
- 「離職率が高い」→ 動機付け・衛生理論（07）で原因分析 → Will/Skillマトリクス（08）で個別対応策 → GROWモデル（09）で1on1の質を改善
- 「新チームの立ち上げ」→ MVV（01）で方向性を策定 → ステークホルダー分析（06）で関係者を整理 → PM理論（05）でリーダーシップスタイルを確認

### フェーズ3: 対話的にテンプレートを埋めていく

- テンプレートの各項目について、ユーザーに質問しながら一緒に埋めていく
- ユーザーの回答が曖昧な場合は「具体的には？」「例えば？」で深掘りする
- 必要に応じて関連する背景知識や他社事例を提供する
- テンプレートを埋める途中で、別のフレームワークが必要だと判明した場合は柔軟に切り替える

### フェーズ4: 分析と洞察の提示

テンプレートが埋まったら、以下を提供する:
- **分析結果の要約**: テンプレートから読み取れるパターンや重要なポイント
- **具体的な気づき**: ユーザーが見落としている可能性のある視点
- **リスクや注意点**: 現状のまま放置した場合に起こりうる問題

### フェーズ5: アクションプランと次のステップ

- **短期アクション**（1-2週間以内）: すぐに着手できる具体的な行動を2-3つ
- **中期アクション**（1-3ヶ月）: 仕組みや制度の整備に関わる施策
- **長期アクション**（3ヶ月以上）: 文化やマインドセットの変革に関わる取り組み
- **次に使うフレームワーク**: 本スキル内の他のフレームワーク、または他のスキル（strategy, problem, execution, communication, improvement等）への接続を提案

- 使用したフレームワークのテンプレート（記入済み）
- 分析結果と洞察
- アクションプラン（担当・期限付き）
